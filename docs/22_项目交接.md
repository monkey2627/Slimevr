# motionUse 项目交接

更新日期：2026-10-08

## 核心目标

用五个 SlimeVR IMU 实时预测人体 SMPL 24 关节姿态，并驱动 Unity Avatar：

```text
SlimeVR trackers
  -> SlimeVR-Server / SolarXR
  -> mobileposer.realtime.run
  -> MobilePose (wrists_shanks_waist)
  -> ws://127.0.0.1:21200
  -> Unity official SMPL reference + Humanoid Avatar
```

当前 tracker 与模型标签：

| SlimeVR 绑定 | MobilePose 标签 | 实际位置 |
| --- | --- | --- |
| LEFT_LOWER_ARM | lw | 左手腕/前臂末端 |
| RIGHT_LOWER_ARM | rw | 右手腕/前臂末端 |
| LEFT_FOOT | ls | 左脚踝上方、小腿下端 |
| RIGHT_FOOT | rs | 右脚踝上方、小腿下端 |
| WAIST | waist | 腰部 |

脚踝 tracker 在 SlimeVR 中使用 ankle/foot 绑定，安装方向为 `Front-Right`。训练布局名称虽然是
`wrists_shanks_waist`，但当前映射已经按实际训练 checkpoint 验证，不要擅自改成不存在的
`LEFT_LOWER_LEG` / `RIGHT_LOWER_LEG`。

## 当前核心问题

**模型输出的自然站立姿态本身仍有明显误差。** 典型问题包括：

- 自然站立时手臂、躯干或双脚姿态不标准；
- 抬腿和踢腿幅度明显不足；
- 深蹲、跪姿、四点支撑、仰卧和死虫动作误差很大；
- 大腿、上臂、髋、膝和肘等未直接观测关节容易产生错误推断。

由于连自然站立都不正确，现阶段不能只归因于“五 IMU 信息不足”。更可能还存在实时传感器安装参考与
训练数据之间的固定旋转偏差，尤其是 pitch/roll；当前 heading calibration 主要估计 yaw，不能自动消除
完整的三轴 mounting offset。

## 已经确认的结论

1. SolarXR 通信链路已稳定，Python 到 Unity 的 WebSocket 不是主要问题。
2. `data/raw/ours` 同一采集经过离线 prepare 与实时预处理的 `feature[60]` 基本一致：
   - 1862 帧；
   - orientation RMSE 约 `1.0e-8`；
   - acceleration RMSE 约 `1.145e-4`；
   - feature RMSE 约 `5.72e-5`。
3. 上述结果只证明“两套预处理代码一致”，**不能证明当前 SolarXR 实时输入与训练采集分布一致**。
4. Python Web SMPL 表面、Unity 官方 SMPL 直驱、Unity Humanoid Avatar 的表现基本一致。
5. 因此 SMPL -> Humanoid 重定向不是当前主要误差来源，错误已经存在于 MobilePose 输出中。
6. Unity 末端 T-pose、relaxed-arms 校准只能让某个姿势看起来正确，不能修复模型输出，并可能破坏其他姿势。
7. 脚接触、关节限位、膝盖方向、脚底 IK 和骨长约束只能限制不合理结果，不能从五个 IMU 唯一恢复缺失姿态。

## 下一步最高优先级

只研究自然站立，不继续调整 Unity 校准或盲目加约束：

1. 录制当前真实 SolarXR 自然站立 10 秒，保存 raw quaternion、reference-adjusted quaternion、acceleration
   和最终 `feature[60]`。
2. 从 `data/raw/ours` 选择自然站立片段，在相同 30 FPS 时间点生成相同特征。
3. 逐 tracker 比较实时与训练站立姿态的固定旋转差，输出 yaw/pitch/roll 与总角度差。
4. 判断差值是否在多次佩戴、重启和 SlimeVR 校准后仍稳定。
5. 若偏差稳定，在**模型输入前**加入可开关的每 tracker 三轴 mounting-reference calibration，并做 A/B 测试。
6. 只有自然站立修正后仍存在抬腿/蹲跪错误，才进入真实 SlimeVR 数据再微调和动作覆盖扩充。

建议新增的第一个功能：网页中的 `Live neutral vs data/raw/ours neutral` 面板，展示每个 tracker 的旋转差，
并允许导出诊断 JSON。不要先自动应用修正；先观察数据并验证偏差稳定性。

## 启动方式

Python 环境：

```text
D:\Software\anaconda\envs\mobileposer\python.exe
```

推荐基线 checkpoint：

```text
results\ours_multi_finetune\layouts\wrists_shanks_waist\model_finetuned.pth
```

PowerShell：

```powershell
cd D:\dyh\MotionRe\motionUse
conda activate mobileposer
python -m mobileposer.realtime.run `
  --checkpoint "D:\dyh\MotionRe\motionUse\results\ours_multi_finetune\layouts\wrists_shanks_waist\model_finetuned.pth" `
  --calibration-frames 150 `
  --output-fps 30 `
  --include-contact `
  --contact-interval 60 `
  --web
```

网页：`http://127.0.0.1:8765/`

Unity：打开 `IMUTrack-for-Spine/Assets/Scenes/AvatarScene.unity`。场景中已有：

- 原 Humanoid Avatar + `MobilePoserPoseSource`；
- `MobilePoser SMPL Reference` + `MobilePoserSmplPoseSource`。

两个 Unity 组件都会连接 `ws://127.0.0.1:21200`，可以并排 A/B。官方 SMPL 直驱不需要点击 T-pose
或 relaxed-arms 校准。基线测试应关闭所有 Unity 后处理约束。

## Web 与录制能力

`--web` 页面支持：

- Front / Side 火柴人；
- 可旋转缩放的 3D joints；
- 6890 顶点官方 SMPL surface（WebGL GPU 蒙皮）；
- 输出姿态录制、停止、回放与 JSONL 下载；
- 离线 prepare 与实时预处理的 feature 比较。

Python 原始输入录制与离线回放仍以 `mobileposer/realtime/` 下现有 recorder/replay 工具为准。

```text

├─ mobileposer/                 Python 模型、训练、实时推理和 Web 诊断

├─ IMUTrack-for-Spine/         Unity 2022.3 项目

├─ SlimeVR-Server/             可修改和打包的 SlimeVR Server 源码
├─ solarxr_protocol/           Python 使用的 SolarXR 协议生成代码
├─ configs/                    项目配置
├─ tests/                      Python 测试
├─ data/                       本地数据集（被 Git 忽略）
├─ results/                    checkpoint 与实验结果（被 Git 忽略）
```

- `SlimeVR-Server/solarxr-protocol` 属于 SlimeVR pnpm workspace；
- 根目录 `solarxr_protocol/` 是 Python 客户端实际使用的生成代码。

## 接手注意事项

- 同时只运行一个 `mobileposer.realtime.run`。
- Unity 中每个 Avatar 只保留一个对应 PoseSource；并排 A/B 时官方 SMPL 和 Humanoid 各一个是预期状态。
- 不要把 tracker 的绝对旋转直接当作任意 Humanoid 骨骼旋转。
- 不要用 Unity 站立校准掩盖 Python 输出错误。
- 任何输入修正都必须可开关，并保留未修正基线与录制回放。
- 当前仓库可能包含大数据、checkpoint、Unity Library 和 Node modules；它们均不应加入 Git。
