# 数据采集到微调实时使用链路审计报告

审计范围：SlimeVR Server → IMUTrack-for-Spine Unity 录制 → `data/raw/ours` → 真实录制微调 → `mobileposer.realtime.run` 实时推理。

审计方式：只读对照流程文档、Python/C#/Kotlin 源码、已有录制包和已有微调产物；没有修改代码或原流程文档。

## 结论

整体数据流可以闭合，但两份流程文档不能直接作为当前实现的精确操作手册。最重要的结论如下：

1. 录制包的文件职责和 Unity/SlimeVR 的总体链路描述基本正确。
2. 真实录制微调实际走 `mobileposer.prepare_ours_no_head` + `mobileposer.finetune_ours_multi`，不是文档中以 `PoseDataset`、125 帧窗口和 `train.py` 为主的标准合成数据训练链路。
3. 训练和实时推理的核心 60 维特征排列是一致的：`[5 个加速度 / 30 | 5 个 3x3 姿态矩阵]`，不是交错的每传感器 12 维。
4. `wrists_shanks_waist` 必须使用并按顺序绑定：左前臂/腕、右前臂/腕、左小腿、右小腿、腰部。
5. 用户给出的实时命令含有错误参数 `--web5`。当前入口只注册 `--web`，原命令会在模型启动前因未知参数退出。
6. 已存在目标微调文件：`results/ours_multi_finetune/layouts/wrists_shanks_waist/model_finetuned.pth`。静态检查确认路径和布局命名匹配；本机 Python 环境缺少 `torch`，未能完成运行时加载验证。

## 一、录制和动作包

`11_IMU到动作导出全链路.md` 对“Tracker → SlimeVR → HumanSkeleton → VMC → Unity → 动作包”的分层描述与当前代码结构相符。现有录制包也包含：

- `manifest.json`
- `*_motion.json`
- `*_tracker.json`
- `*_raw-imu.json`
- `*_keyframes.json`

例如 `data/raw/ours/3_站位/1/manifest.json` 声明了上述文件、SHA256、`rawImuFrameCount=1863` 和 `rawImuSensorCount=17`。这说明 raw IMU 与动作姿态是同一录制中的并行产物，不是由 `motion.json` 二次推导出来的。

文档需要补充或收紧以下表述：

- 文档中的 Server 路径是 Linux 旧路径，当前工作区实际目录是 `SlimeVR-Server`；入口文件描述应以当前检出的版本为准。
- `raw-imu.json` 的 `linear`/线性加速度不是裸三轴加速度。当前真实数据预处理会把已处于共享世界坐标的线性加速度直接作为输入；只有标记为 `raw` 的加速度才会再按记录姿态从设备坐标旋转到世界坐标。不能笼统写成“所有 raw IMU 都需要旋转”。
- 录制包帧数、采样率和 Unity Avatar 帧数不能仅凭文件名假定一致；下游实际会按共同有效长度截断，并将输入处理到 30 FPS。

## 二、真实录制到微调

实际入口和职责如下：

### `prepare_ours_no_head.py`

- 从 manifest 找到 `raw-imu.json` 和 `tracker.json`。
- 读取已有的 SMPL 拟合目标。
- 默认 `--input-source raw-imu`，读取物理 IMU；`tracker-json` 只是另一种显式模式。
- 按采样率降采样到 30 FPS。
- 将加速度乘以重力常数转换为 `m/s²`，对 raw 加速度做设备到世界旋转；已是 SlimeVR 线性加速度的信号不重复旋转。
- 使用首段在线帧估计 tracker-to-bone 旋转，并去除加速度静态偏置。
- 应用 Unity/SMPL/训练世界坐标变换。
- 为每个可用布局写出 `ours.pt`，其中前五个 slot 是真实布局传感器。

### `finetune_ours_multi.py`

该脚本递归发现所有 `manifest.json`，调用真实录制预处理，然后对每个布局联合训练：

- 输入构造为 `torch.cat(((acc/30).flatten(1), ori.flatten(1)), -1)`，即 60 维。
- 检查布局标签顺序和 input/target 时间戳一致。
- 只训练 `joints` 与 `pose` 模块。
- `velocity`、`contact` 及其它冻结权重保持不变。
- 每个 epoch 以完整录制序列训练，不是标准 `PoseDataset` 的 125 帧切窗训练。
- checkpoint 选择指标使用全部采集动作，没有独立 holdout 验证集，因此结果可能过拟合已有动作。

因此，`10_训练数据流与模型输入.md` 中关于 AMASS/DIP 合成数据、`PoseDataset`、125 帧窗口和标准 `train.py` 的描述，适用于基础模型/合成数据训练，但不能直接代表当前“真实录制微调”流程。文档应把这两条流程明确拆开。

## 三、训练和实时输入的一致性

已确认一致的部分：

| 项目 | 真实微调 | 实时推理 |
|---|---|---|
| 采样率 | 30 FPS | `--output-fps 30` |
| 传感器数量 | 5 | 精确匹配一个五传感器布局 |
| 特征排列 | `acc.flatten / 30` 后接 `ori.flatten` | 同样先加速度、后姿态 |
| 输入维度 | 15 + 45 = 60 | 15 + 45 = 60 |
| `wrists_shanks_waist` 顺序 | `lw,rw,ls,rs,waist` | 同一布局顺序 |
| 姿态来源 | bone-calibrated rotation | `rotation_reference_adjusted` 经实时坐标变换 |

实时推理还会执行：

- 根据 SolarXR BodyPart 集合自动识别布局；不接受“最接近布局”。
- 启动时收集 150 帧 heading calibration；需要有多轴旋转，静止不动可能失败。
- 使用 45 帧滑窗；模型输出相对最新输入存在约 4 帧固有延迟。
- `--include-contact` 从同一个 combined checkpoint 加载脚接触模块。

## 四、必须修正的实时命令

当前命令中的 `--web5` 无效。可用命令是：

```powershell
python -m mobileposer.realtime.run `
  --checkpoint "D:\dyh\MotionRe\base_mobileposer\results\ours_multi_finetune\layouts\wrists_shanks_waist\model_finetuned.pth" `
  --calibration-frames 150 `
  --output-fps 30 `
  --include-contact `
  --contact-interval 60 `
  --web
```

`--web` 只启用浏览器可视化；默认 HTTP 端口是 `8765`。`--contact-interval 60` 只控制脚接触重新计算频率，不改变主体姿态模型的输入频率。

在执行前还必须确认 SlimeVR 中在线 tracker 的 BodyPart 集合恰好是：

```text
LEFT_LOWER_ARM, RIGHT_LOWER_ARM,
LEFT_LOWER_LEG, RIGHT_LOWER_LEG,
WAIST
```

否则实时入口会拒绝解析布局，或解析为另一个已训练布局。

## 最终判定

在修正 `--web5` 为 `--web`、确认 tracker BodyPart 绑定和实时 heading calibration 成功的前提下，当前“真实录制 → 真实输入预处理 → `wrists_shanks_waist` 微调模型 → 实时推理”的数据排列和主要坐标/缩放约定是一致的。

不能把当前流程表述成“录制出的 motion 直接进入标准 PoseDataset 训练”；真实微调实际使用 raw IMU 加校准后的输入和 SMPL/Avatar 目标，训练策略也与标准合成数据训练不同。
